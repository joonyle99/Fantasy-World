FantasyWorld · 프로젝트 노트

Assembly Definition (asmdef) 이해하기

Assets/Scripts/FantasyWorld.asmdef 를 왜 만들었고, 참조를 걸면 컴파일이 어떻게 동작하는지 정리.

1. 한 줄 요약

asmdef = “이 폴더 하위 스크립트를 별도의 .dll 로 컴파일해라” 라고 Unity에 알려주는 표식. 우리는 Assets/Scripts/ 안의 게임 로직을 FantasyWorld.dll 이라는 독립 묶음으로 격리하려고 만들었다.

2. C# 컴파일의 최소 단위는 “파일”이 아니라 “어셈블리(dll)”

C# 컴파일러(Roslyn)는 “한 어셈블리에 속한 .cs 파일 전부를 입력받아 .dll 하나를 출력” 하는 방식으로 동작한다. 파일별로 조각을 만들어 붙이지 않는다.

파일들이 서로 타입을 참조하기 때문(예: GooseController 가 InputService, AudioService 를 사용)에 타입 검사·오버로드 결정·메타데이터 생성을 하려면 전체를 한꺼번에 봐야 한다. 그래서 항상 어셈블리 단위로 처리된다.

결론: 파일 하나만 고쳐도, 그 파일이 속한 어셈블리 전체가 다시 컴파일된다. 파일 단위로 못 쪼개니, 속도를 위해선 “굽는 덩어리 자체를 작게” 만드는 수밖에 없다. 그게 asmdef의 역할.

3. asmdef 없을 때 vs 있을 때

없을 때

Assets/ 아래 asmdef 없는 스크립트는 전부 Assembly-CSharp.dll 하나로 뭉친다.

Assembly-CSharp.dll ├─ 내 게임 코드 (Assets/Scripts/*) └─ Assets/Plugins/ithappy/Animals_FREE/Scripts/*.cs ← asmdef 없는 플러그인

→ GooseController.cs 한 줄 수정 시 내 코드 + ithappy 스크립트까지 전부 재컴파일.

있을 때 (현재 상태)

FantasyWorld.dll ← Assets/Scripts/ 안의 파일만 Assembly-CSharp.dll ← ithappy 등 느슨한 플러그인 스크립트만 남음

→ GooseController.cs 수정 시 FantasyWorld.dll 만 재컴파일. ithappy는 건드리지 않음.

주의: VContainer · FMOD · JoonyleGameDevKit 같은 패키지는 자기 asmdef를 이미 갖고 있어 원래부터 별도 dll이다. 내 코드를 고쳐도 걔넨 재컴파일되지 않는다. 이건 내 asmdef의 효과가 아니다.

4. references 를 걸면 실제로 벌어지는 일

현재 FantasyWorld.asmdef 의 참조 목록:

{
  "name": "FantasyWorld",
  "references": [
    "VContainer",
    "Joonyle.GameDevKit",
    "UniTask",
    "FMODUnity",
    "Unity.InputSystem"
  ]
}

4-1. Unity가 의존 그래프를 만든다

프로젝트의 모든 asmdef를 스캔해 “누가 누구를 참조하는지” 그래프를 그린다.

VContainer.dll ─┐ FMOD.dll ───────┼─► FantasyWorld.dll (아무도 FantasyWorld를 참조하지 않음) Joonyle.dll ────┘

4-2. 위상 정렬 → 컴파일 순서 결정

  1. UniTask.dll, Unity.InputSystem.dll … (남에게 의존 안 함)
  2. VContainer.dll, FMODUnity.dll, Joonyle.GameDevKit.dll
  3. FantasyWorld.dll ← 마지막. 위 것들이 있어야 컴파일 가능

결과물은 전부 Library/ScriptAssemblies/ 에 .dll 로 쌓인다.

4-3. FantasyWorld.dll 컴파일 시 컴파일러 호출 (개념)

csc  Assets/Scripts/Game/GameFlow.cs
     Assets/Scripts/Core/AudioService.cs
     ... (21개 파일 전부)
     -reference:Library/ScriptAssemblies/VContainer.dll
     -reference:Library/ScriptAssemblies/FMODUnity.dll
     -reference:Library/ScriptAssemblies/Joonyle.GameDevKit.dll
     -reference:.../UniTask.dll
     -reference:.../Unity.InputSystem.dll
     -out:Library/ScriptAssemblies/FantasyWorld.dll

references 항목 하나당 -reference: 플래그 하나. 이게 참조의 실체.

4-4. -reference 가 컴파일러 안에서 하는 일

지정된 dll의 public 타입 메타데이터를 읽어 심볼 테이블에 올린다.

using VContainer.Unity;                 // VContainer.dll 에 존재 → OK
public sealed class GameFlow : IStartable   // IStartable 은 VContainer.dll → OK

references 에서 VContainer 를 빼면 -reference 가 안 붙고 → error CS0246: The type or namespace name 'IStartable' could not be found

4-5. 참조는 단방향 · 순환 금지

  • FantasyWorld → VContainer : FantasyWorld는 VContainer의 public 타입을 본다
  • 반대로 VContainer 는 FantasyWorld 의 존재를 모른다 → 내 코드가 바뀌어도 VContainer는 재컴파일 안 됨
  • 서로 참조(순환)는 Unity가 금지

5. 참조에 무엇을 넣을까 — 두 가지 질문을 구분하라

“패키지가 자기 asmdef를 갖고 있으면 참조 안 해도 된다”는 말은 절반만 맞다. 서로 다른 두 문제를 섞으면 헷갈린다.

질문답
A. 패키지 X가 내 코드 수정 시 재컴파일되나? X가 자기 asmdef를 가지면 안 된다. 내 references 와 무관.
B. 내 코드가 X의 타입을 using 할 수 있나? 내 references 에 X를 넣어야만 가능하다. X가 asmdef를 갖든 말든 무관.

올바른 기준

내 코드에서 using 하는 게 있으면 → 참조에 넣는다. 아니면 안 넣는다. “asmdef를 가졌는지”는 판단 기준이 아니다.

패키지내 코드에서 쓰나?참조?
VContainerLifetimeScope, [Inject], IStartable✅
Joonyle.GameDevKitGameStateController<T>✅
FMODUnityAudioService 에서 FMOD API✅
Unity.InputSystemInputService✅
UniTask나중에 async 로딩 (지금은 예약)✅ (미리)
vHierarchy / vTabs안 씀 (에디터가 알아서 동작)❌
vInspector[Button] 등 어트리뷰트 쓸 때만상황따라

왜 예전 방식(Assets/Scripts 에 그냥 넣기)에선 이게 필요 없었나

asmdef 없는 코드(Assembly-CSharp)에는 autoReferenced: true 인 모든 어셈블리가 자동으로 참조에 들어가 있다. 그래서 아무거나 using 해도 됐다.

asmdef를 만들면 이 자동 참조가 꺼진다 → 쓰는 것만 직접 나열해야 한다. VContainer 등을 references 에 넣은 것은 그 나열 작업이다. 안 넣으면 IStartable 등이 CS0246 컴파일 에러.

참고: vHierarchy 를 참조에 안 넣은 이유는 “걔가 asmdef를 가져서”가 아니라 “내 코드가 걔 타입을 안 써서” 다. 판단 기준을 헷갈리지 말 것.

6. 재컴파일이 번지는 범위

어셈블리를 수정하면 그 어셈블리 + 그것을 참조하는 하류(downstream) 만 재컴파일된다. 참조당하는 상류는 그대로.

수정한 파일재컴파일되는 dll이유
Game/GameFlow.csFantasyWorld.dll 만FantasyWorld를 참조하는 어셈블리 없음
VContainer 패키지FantasyWorld.dll (하류 전부)FantasyWorld가 VContainer를 참조 → 상류가 바뀌면 하류로 전파
ithappy 플러그인 .csAssembly-CSharp.dll 만FantasyWorld와 분리돼 있음

7. 그래서 이 프로젝트에서 asmdef를 만든 이유

  1. 내 게임 로직(Assets/Scripts/)을 Assembly-CSharp.dll 에서 떼어내 FantasyWorld.dll 로 격리 — 느슨한 플러그인 스크립트와 서로 재컴파일을 끌고 다니지 않게.
  2. 나중에 내 코드를 여러 어셈블리로 쪼갤 진입점 — asmdef가 하나라도 있어야 거기서 갈라진다. (진짜 목적)
  3. 참조 경계 강제 — references 에 없으면 using 자체가 안 되므로 실수로 엉뚱한 의존이 생기는 걸 컴파일 단계에서 차단.
솔직한 평가: 지금은 스크립트가 몇 개 없어서 컴파일 속도 이득은 미미하다. asmdef의 값어치는 “프로젝트가 커졌을 때 내 코드를 나누기 위한 발판”이다.

8. 앞으로: 코드가 늘면 이렇게 쪼갠다

Assets/Scripts/ 안에 또 다른 asmdef를 두면 거기서부터 별도 dll로 갈라진다.

Assets/Scripts/ FantasyWorld.asmdef ← Core/, Game/ 담당 Gameplay/ FantasyWorld.Gameplay.asmdef ← 여기부터 별도 dll (FantasyWorld.Gameplay.dll) UI/ FantasyWorld.UI.asmdef

의존 그래프 예:

VContainer.dll ─┐ FMOD.dll ───────┼─► Core.dll ─┬─► Gameplay.dll └─► UI.dll

전략: 자주 고치는 코드(Gameplay, UI)는 그래프의 잎(아래)에, 잘 안 바뀌는 공용 코드(Core)는 위에 둔다. Core를 건드리면 하류로 다 번지므로 Core는 최대한 안정화시킨다.

9. 되돌리기

부담되면 FantasyWorld.asmdef 와 .meta 를 지우면 된다. 그러면 Assets/Scripts/ 전체가 다시 Assembly-CSharp.dll 로 합쳐지고, 패키지들은 자동으로 보이게 된다(참조 명시 불필요). 프로젝트가 커지면 결국 다시 나누게 되므로 두는 편을 권장.
